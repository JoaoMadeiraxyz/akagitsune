# connection-lifecycle Specification

## Purpose
Defines how a WebSocket connection is accepted by the gateway, how it learns the identity the gateway assigned to it, and which frames end it at admission level.

## Requirements

### Requirement: Connecting is joining
The gateway SHALL accept WebSocket upgrades on `GET /ws` without any in-band handshake, and SHALL send the new connection a `{"type":"welcome","id":"<uuid>"}` text frame as its first frame, where `id` is a UUID generated by the gateway for that connection. A new connection SHALL have no subscriptions. That UUID is the only identity the connection has, and it is the `from` value of every text frame and the sender bytes of every binary frame the connection publishes.

Fonte: `src/lib.rs:13` — `app`; `src/ws.rs:53` — `handle_socket`; `src/protocol.rs:14` — `ServerMessage`.
Teste: `tests/gateway.rs:114` — `connection_is_welcomed_with_an_id`; `tests/gateway.rs:164` — `payload_is_relayed_verbatim_to_others`.

#### Scenario: New connection receives its identity
- **WHEN** a client opens a WebSocket to `/ws` and sends nothing
- **THEN** the first frame it receives is a text frame `{"type":"welcome","id":"<uuid>"}` whose `id` parses as a UUID

#### Scenario: Assigned identity is the sender of relayed frames
- **WHEN** a connection welcomed with id `X` publishes a valid text frame to a topic another connection is subscribed to
- **THEN** that subscriber receives it with `"from":"X"`

### Requirement: Frames above 64 KiB terminate the connection
The gateway SHALL accept inbound frames whose payload is at most 65536 bytes, counting the whole frame: the control frame around `data` for text, and the topic header for binary. A frame larger than that SHALL terminate the sending connection without a WebSocket close handshake, and SHALL NOT be delivered to any other connection.

Fonte: `src/ws.rs:26` — `MAX_MESSAGE_SIZE`; `src/ws.rs:36` — `websocket_handler`; `src/ws.rs:164` — `read_loop`.
Teste: `tests/gateway.rs:121` — `frame_at_size_limit_is_relayed`; `tests/gateway.rs:140` — `oversized_frame_drops_the_sender_without_relaying`.

#### Scenario: Frame at the limit is relayed
- **WHEN** connection B is subscribed to `k`
- **AND** connection A sends a `publish` text frame to `k` whose total length is exactly 65536 bytes
- **THEN** B receives it in a `message` envelope with A's `data` embedded byte for byte

#### Scenario: Oversized frame drops the sender
- **WHEN** connection B is subscribed to `k`
- **AND** connection A sends a `publish` text frame to `k` whose total length is 65537 bytes
- **THEN** A's connection ends without A receiving a close frame
- **AND** B receives nothing for that frame
